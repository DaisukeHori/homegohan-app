# 本番 RLS ドリフト調査（2026-10-06）— #1243

本番 Supabase（`flmeolcfutuwwbjmzyoz`）の認可まわりの状態と、`supabase/migrations/` が定義する状態を比較した結果。
「本番に揃えるか / ファイル側に揃えるか」は各差分ごとに **推奨** を書いているが、判断と対応（migration 化）は別途行う。

## 1. 結論

- **本番にだけある認可オブジェクトは 7 件**（関数 1、storage バケット 2、storage ポリシー 4）。
  - **critical: 旧 `promote_child_to_user(p_member_id uuid, p_user_id uuid)`** が SECURITY DEFINER のまま本番に残り、**anon にも EXECUTE 権限**がある。`20260511000135` で DROP 済みのはずの関数で、migration 外で再作成されたとみられる。#1232 で指摘された抜け道が本番で現存している。
- **本番にだけある RLS ポリシー（public スキーマ）は 0 本。** #1243 本文が「migration に定義が無い」とした support / shopping_list / challenge_participants / app_logs / ai_content_logs / system_daily_stats / segment / metric 系のポリシーは、すべて `20260511000137_backfill_oob_remaining.sql` に同名・同定義で存在する（`"public"."テーブル名"` の引用符付き表記のため、単純な検索では見つからなかった）。
- **定義が違うものは 13 本**。12 本は実質同等（対象ロールと UPDATE の WITH CHECK の書き方の差）、1 本は本番の方が狭い（家族スコープの監査ログが見えない）。
- テーブルの RLS 有効状態、anon / authenticated へのテーブル GRANT、migration が定義する関数の SECURITY DEFINER / `search_path` / EXECUTE 権限は、本番と一致した。

| 分類 | 件数 | 最大の危険度 |
|---|---|---|
| 本番のみ | 7（関数 1 / storage バケット 2 / storage ポリシー 4） | **critical**（P-1） |
| ローカルのみ（migration にあるのに本番に無い） | 0 | — |
| 両方にあるが定義が違う | 13（RLS ポリシー） | 低 |

## 2. 方法

### 本番側のデータ

`.github/workflows/prod-schema-snapshot.yml` で **2026-10-06T18:43:16Z** に読み取り専用で取得したカタログ（`supabase/baseline/catalog/`）。

- `pg_policies`（全スキーマ）、public の関数の SECURITY DEFINER / `proconfig` / 所有者 / `proacl`、public・storage のテーブルの RLS 有効状態と `relacl`、storage のバケット設定
- 照会は `BEGIN TRANSACTION READ ONLY` 内で実行して ROLLBACK（`scripts/baseline/snapshot_catalog.sql`）。本番への書き込みは無い
- 当初の想定は「読み取り専用 Supabase コネクタで取得」だったが、作業セッションに読み取り専用コネクタが無かった（書き込み可能なコネクタは使用禁止）ため、CI の読み取り専用ジョブで代替した

### migration 側の「定義された状態」

`supabase/migrations/` は空 DB から再生できない（#1116。121 本中 64 本が失敗）ため、次の手順で再現した（`scripts/baseline/drift_report.sh`）。

1. 本番スキーマのベースライン（`supabase/baseline/`）だけを適用したローカル DB を作る
2. public の RLS ポリシーを全削除し、RLS を全テーブルで解除し、テーブル GRANT と関数の EXECUTE 権限を新規作成時の既定に戻す（`scripts/baseline/drift_reset_security.sql`。テーブル・型・関数の構造は本番のまま）
3. 121 本の migration を順にすべて再適用する（既存オブジェクトとの衝突エラーは許容し、トランザクション内でも文単位で続行）
4. カタログを取り出し、本番カタログと比較する（`scripts/baseline/drift_compare.py`）

storage のポリシーは、ローカルでは `postgres` が `storage.objects` の所有者でなく再適用できないため、storage に触れる migration 2 本（`20260111000000_health_checkups.sql` / `20260511000000_recreate_missing_health_checkups.sql`）を目視で比較した。

## 7. 限界

- 「migration が定義する状態」は、本番と同じテーブル構造の上で migration を再適用して再現したもの。再適用中のエラーは 50 件で、内訳は既存オブジェクトとの衝突（already exists 等）が大半。認可状態の判定に影響するものは無いことを確認した（関数名の重複による COMMENT / 権限文の失敗 4 件は、COMMENT か後で DROP される旧関数に対するもの。既定値の差による CREATE OR REPLACE 失敗 1 件は、後続の migration で同じ関数が定義し直されている）。
- 関数の本体（処理内容）の差は比較していない（比較対象は SECURITY DEFINER / `search_path` / EXECUTE 権限）。
- テーブル GRANT は anon / authenticated の権限だけを比較した。
- 本番にだけある関数の判定は「同名の CREATE FUNCTION が migration にあるか」で行っている。同名で引数だけ違う関数が本番にだけある場合も検出できるよう、オーバーロードは個別に確認した（本番でオーバーロードがあるのは `promote_child_to_user` のみ）。

### 再確認で見つけて直したもの

- ベースラインの作成でテーブルの権限が本番どおりにならなかった。pg_dump の権限出力だけでは Supabase の既定権限（anon / authenticated への自動付与）が残り、本番で外した `family_promotion_requests`（#1232）のテーブル権限がローカルで復活していた。`prod_table_acl.sql` を追加して直した（`supabase/baseline/README.md` の「忠実度」）
- ローカルの `db reset` が、再起動で IP アドレスが変わった Storage に Kong が古い IP で接続し続けて止まることがあった。`scripts/supabase-local.sh` で Kong を再起動して待つようにした

### この比較の限界（変わらず）

- 列・インデックス・制約・トリガーなど、テーブル構造全体は比べていない。migration を空の DB から流し直せなかったため（#1116）。
  #1116 で migration を本番スキーマのベースラインに統合して空の DB から流し直せるようにしたため、以後は CI の `supabase db diff --linked`（main へのマージ後に毎回実行）が、テーブル構造を含む本番全体との差を検出する
- 関数本文の比較は、migration の最後の定義と本番の本文の文字列比較（コメント・空白・大文字小文字を除いた比較を含む）
